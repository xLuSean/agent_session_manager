## 目前結論

### 2026-10-05：清單遺漏 fork 關係的補讀

- 發現 `thread/list(useStateDbOnly=true)` 回傳的 fork 欄位可能為空，但同一對話的 `thread/read(includeTurns=false)` 能回傳來源；只有前者的 UI 因而錯誤地顯示沒有相關 fork。保持清單的禁止掃描修復設定，改以官方逐筆 metadata 讀取補齊全來源圖的 fork 欄位。
- 補讀有筆數、整體時間及單次等待上限；不讀取 turns，也不更改清單提供的標題、原生狀態、pin 或子代理關係。只有身份相符且明確提供 fork 欄位的回應可標示已知；欄位缺席、失敗、衝突或超出上限均顯示關係不完整，不阻擋其他項目的既有操作檢查。
- Fork 來源是分支沿革，不等同於目前每一個共享歷史片段的引用；畫面改為待檢視的 fork，不宣稱所有同源 fork 都是已證實的阻擋者。它只用於導覽及已確認選取內的排序，未授權的分支不會加入刪除。
- 本機唯讀診斷確認清單漏掉的兩筆 fork 可由官方逐筆查詢找回；正式刪除請求為零。30 項針對性核心回歸及 3 項 App 回歸通過，涵蓋 null／缺欄位、身份／來源衝突、失敗、上限、保護狀態保留及 fork 排序。私人標題與 ID 未寫入版本控制。
- 本節記錄基於 `0.1.117-alpha.1 (36)` 的原始碼驗證；後續候選版本、來源提交與雜湊以 `dist/` 中的候選版 JSON 為準。
